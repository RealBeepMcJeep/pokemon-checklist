# Managed backend comparison for the family species app

**Checked:** 18 September 2026 (America/Phoenix). Prices and quotas change; the linked vendor page is authoritative. “No server code” means a static browser SPA can authenticate, authorize per-user/shared data, and sync safely without an owner-operated API/worker. A static host is still needed, but that can be GitHub Pages/Cloudflare Pages/etc.

## Recommendation in one paragraph

For this app, the strongest choices are **Firebase Realtime Database on Spark** (simplest genuinely serverless browser path, no card, no per-document read billing; 100 simultaneous connections is ample) or **Supabase Free** (better SQL/export/RLS, browser SDK, 50k MAU and 2M realtime messages, but it pauses after one week idle). Use one small current-state document, not an ever-growing event log, on either. If “never pause” matters, Firebase RTDB is preferable. Firestore is also viable but bills document reads and requires Blaze for some products/features. Most local-first/sync products below are not complete no-server backends: they need a database, auth service, server-side authorization, or a paid/alpha cloud.

## Baseline requirements and billing model

The payload (tens of KB, ~807 statuses, roughly 5 accounts, a few writes/day) is tiny. The decisive questions are Google OAuth in a static browser, shared-data authorization, offline cache, and whether reconnecting reads an entire log. A design that reads one current JSON document per device/day is cheap everywhere; an append-only event log is expensive on document/row-read meters and can become operationally awkward.

## Direct answers

### (a) Which can host this at genuinely zero cost with no server code?

1. **Firebase Realtime Database + Firebase Auth + Google provider (Spark)** — the clearest answer. No card, browser SDK, Security Rules, 1 GB/10 GB/month/100 connections; no per-document read meter. Host the static SPA separately.
2. **Firebase Firestore + Auth (Spark)** — also no server code and no card, within 50k reads/day/20k writes/day/1 GiB/10 GiB, but document-read billing makes an event log a bad design and some Firebase features require Blaze.
3. **Supabase Free** — browser Google OAuth, RLS, realtime, no custom server, and ample quotas; not “always available” because inactive free projects pause after one week. It is zero-dollar while active and within quotas.
4. **Back4App Free** — browser Parse SDK/Google/ACL/LiveQuery and no card; 25k requests/month, 250 MB DB, 1 GB transfer/files. Confirm LiveQuery behavior and quota in a proof-of-concept.
5. **Nhost Free** — technically browser GraphQL/OAuth/realtime and no custom server, but one-week pause and several unlisted quotas make it less certain.
6. **Appwrite Cloud Free** — likely, but current free database quota/card policy was not sufficiently published to call it “genuinely zero-cost forever” without console verification.

Cloudflare, Turso, Neon, Xata, Convex, Electric, PowerSync, TinyBase, Jazz and Liveblocks either need a server/auth boundary, are a component rather than a durable backend, have a trial/alpha status, or have unverified quotas.

### (b) Which bill per read and penalize an append-only event log?

- **Firestore:** yes, document reads plus index-entry reads; worst direct fit for repeatedly replaying an event log.
- **Cloudflare D1:** yes, rows read/written; 5M rows/day is generous but a broad event-log query burns quota.
- **Turso:** yes, row reads/writes; 500M/10M monthly is generous, but event-log replay is metered.
- **AWS DynamoDB/AppSync:** yes, request/operation/read-capacity meters; exact cost depends on consistency, item size, indexes and AppSync path.
- **Appwrite Cloud:** current model says database reads/writes are quota-metered, but exact free allowance was not published in the checked page.
- **Firebase RTDB:** **not per document**; downloaded bytes and connection/protocol traffic matter instead, so a small JSON snapshot/event payload is usually easier to reason about.
- **Supabase, Nhost, Neon, Xata:** no published per-document read charge; compute/egress/database resource quotas still apply.
- **Convex/Liveblocks/PowerSync/Electric:** usage is function calls, events/connections, synced data, or retention—not Firestore-style document reads—but an event log can still increase those meters.

### (c) Which pause or delete data when idle?

- **Supabase Free:** pauses after **1 week** inactivity.
- **Nhost Starter:** pauses after **1 week** inactivity.
- **Neon:** compute scales to zero when idle; data is not thereby deleted, but wake latency exists.
- **Xata:** scale-to-zero; current offering shown is a 14-day trial, not a permanent free tier.
- **Firebase RTDB/Firestore, Back4App:** no verified inactivity pause/deletion on the checked official pricing pages.
- **Appwrite, Cloudflare, Turso, Convex, Liveblocks, Electric, PowerSync:** no verified idle-pause/deletion number found; do not infer “never.”
- **InstantDB:** continuity/status issue, not an ordinary idle policy; official 2026 notice makes it unsuitable until revalidated.

### (d) Cheapest and simplest for five accounts syncing daily for years?

**Winner: Firebase Realtime Database on Spark**, with a single small per-family document and a bounded change/version field. It has no card, no inactivity pause documented, no document-read billing, and quotas orders of magnitude above this workload. Use Security Rules to allow only the five Google UIDs.

**Runner-up: Supabase Free** if SQL/RLS/export matters more than uptime after inactivity. It is likely $0 for years if someone opens the app at least weekly; otherwise the project pauses and must be resumed. Use one row per family plus a JSONB snapshot or normalized tables; avoid an event log unless retention is bounded.

**Third: Back4App Free** if Parse/ACL/LiveQuery is attractive and 25k monthly requests is comfortable. It has excellent portability, but the request cap is less comfortable than Firebase for future retries/sync bugs.

Do not choose AWS, Cloudflare+D1, Turso, Electric, PowerSync or TinyBase solely to avoid Firebase reputation: each adds either a server/auth layer, row/operation meters, infrastructure, or operational complexity. Appwrite/Nhost are reasonable pilots but require live-console confirmation of currently published quotas and billing behavior.

## Operational caveats

- Google OAuth does not itself authorize a shared family object. Every candidate needs a rule that maps the authenticated UID to a family ID; never trust a family ID supplied by the browser.
- localStorage as the source of truth means remote conflict policy must be explicit: last-write-wins with revision/timestamp is adequate for one small snapshot, while append-only CRDT/event logs are unnecessary complexity.
- Do not put provider admin/service keys in the SPA. This specifically rules out direct browser access to Neon/Postgres, Turso tokens, D1, and many Xata patterns.
- Realtime is not offline sync. Firebase SDK cache, Parse local datastore, CRDT systems, and PowerSync have materially different guarantees; test two devices editing offline and reconnecting.
- Free-tier figures were checked on 18 Sep 2026. Any item explicitly marked “not published,” “unverified,” or “confirm” must be rechecked in the provider console before production.
